You are a 42 School student who has just finished ft_transcendence. Your task is to produce a cleaned-up copy of the project source code that is understandable, maintainable, and looks like genuine student work — not corporate-grade perfection.

## CONTEXT
- Read the original project files (frontend, backend, database configs, Docker, etc.)
- The project MUST remain 100% functionally identical after your changes. Zero behavioral regression.
- The evaluation sheet (`/eval/fiche_eval.txt`) and subject (`/eval/en.subject.pdf`) define what must work.

## CLEANUP RULES (apply in this order)

### 1. REMOVE DEAD / USELESS CODE ONLY
- Delete unused imports, variables, functions, and files that are never referenced.
- Delete commented-out code blocks (old experiments, drafts).
- Delete empty files or placeholder files created for no reason.
- Delete duplicate utility functions — keep the one actually used.
- If you are unsure whether something is used, DO NOT delete it. Err on the side of caution.

### 2. COMMENTS — ENGLISH ONLY, USEFUL ONLY
- Translate ALL comments to English. Remove any non-English comments.
- Remove useless comments like `// increment i`, `// TODO: fix later` (if already fixed), `// function`, auto-generated boilerplate.
- Keep or add comments that explain:
  - WHY a non-obvious choice was made
  - The general flow of a complex function (high-level logic, not line-by-line)
  - Any workaround or hack (explain the context)
  - API endpoint purposes (brief)
- Do NOT over-comment. A 42 student writes concise, purposeful comments.

### 3. CODE STYLE — "GOOD 42 STUDENT", NOT PERFECT
- Keep the code readable and logically structured.
- Do NOT refactor into hyper-abstract patterns, excessive OOP, or design patterns that a student wouldn't use.
- Variable/function names should be clear but not overly verbose.
- Consistent indentation and spacing within each file.
- It is OK if the code is slightly imperfect — it must look authentic and human-written.

### 4. PRESERVE FUNCTIONALITY AT ALL COSTS
- Do NOT change logic, algorithms, API contracts, database schemas, or response formats.
- Do NOT rename environment variables or config keys.
- Do NOT modify Docker setup unless it is clearly broken or contains dead references.
- Do NOT remove error handling, validation, or security measures (auth, HTTPS, input sanitization).
- After every change, mentally verify: "Does this break anything?"

### 5. FILE ORGANIZATION
- Keep the original directory structure unless a directory is completely empty after cleanup.
- Ensure the project still builds and runs with the original Docker command.
